## Provider announcements

### AWS

**AWS Interconnect – multicloud now connects to Microsoft Azure.** Status: GA (announced November 17). It is available in three region pairs: N. Virginia with East US, Frankfurt with Germany West Central, and Sydney with Australia East. Connections can be created from the console, CLI or API. N. California, which was in the preview, is not among the GA regions. Why it matters: AWS now has managed private links to all three of the other big clouds (Google Cloud and OCI went GA earlier this year). Cross-cloud data paths no longer need colocation cross-connects or VPN tunnels you build yourself. ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-announces-AWS-interconnect-multicloud-azure-ga/))

**AWS Lambda adds GPU instances to Lambda Managed Instances.** Status: GA (announced November 18), in all commercial regions that offer both Lambda Managed Instances and EC2 G-series. Supported instances at launch are G4dn, G5, G6, G6f, Gr6, Gr6f and G6e. Pricing has three parts: EC2 On-Demand rates for the instance (Savings Plans and RIs apply), a 9.75% management fee for GPU types (15% for CPU types), and $0.20 per million requests. Why it matters: inference and media-processing steps can stay inside an event-driven Lambda design instead of moving to a separate GPU service. Savings Plans and RIs discount only the EC2 portion, not the management fee. ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-gpu-managed-instances/); [AWS News Blog](https://aws.amazon.com/blogs/aws/aws-lambda-now-supports-gpu-instances-for-event-functions-on-lambda-managed-instances/); [AWS pricing](https://aws.amazon.com/lambda/pricing/))

**Amazon SageMaker AI gets cross-Region inference routing.** Status: GA from November 18, in all commercial regions that support real-time endpoints. A router is a regional resource in your account. It lists endpoints by ARN, which can sit in other regions or accounts, and each endpoint's owner grants access through a resource policy. Every response is tagged with the reason for its routing decision: local-preferred, failover, capacity-available or only-healthy. The router adds no capacity, so it only spreads traffic across endpoints you have already deployed. Why it matters: GPU shortages in one region no longer have to mean failed requests, and you no longer need a custom global load balancer for this. Data-residency rules still apply, so decide which regions may serve which tenants. ([AWS Machine Learning Blog](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/))

### Microsoft Azure

**Azure Cobalt 200 Arm VMs.** Status: GA (Ignite, November 17). The VMs are in 14 regions now, with 23 planned by the end of 2026. Microsoft claims up to 50% better performance than Cobalt 100. The VMs offer consistent-speed and boost modes, and two new families: one for large in-memory databases and one for storage-heavy workloads with up to 23 TB of local storage. Microsoft says Cobalt will be a significant share of new Azure compute capacity in 2027. Why it matters: Arm is becoming the default price-performance option on Azure, as Graviton is on AWS. Multi-arch container builds are now a baseline requirement, not an optimization. ([Azure](https://azure.microsoft.com/en-us/blog/azure-cobalt-200-vms-now-available-proven-on-real-workloads-and-built-for-the-agentic-era/); [The New Stack](https://thenewstack.io/microsoft-cobalt-200-ga/))

**Azure HorizonDB, a distributed PostgreSQL-compatible database.** Status: GA in 13 regions across the Americas, Europe and Asia Pacific (Ignite). Some AI features, such as model management, are still in preview. Fabric HorizonDB, a serverless variant that pauses when idle, is in public preview. Microsoft claims up to 8x the OLTP throughput of self-managed PostgreSQL, and databases of up to 128 TB with built-in vector search. Why it matters: Azure now has a scale-out Postgres to compete with Aurora and AlloyDB. Analysts warn that Fabric HorizonDB's cold starts make it a poor fit for latency-sensitive, customer-facing paths. ([Microsoft Tech Community](https://techcommunity.microsoft.com/blog/adforpostgresql/horizondb-postgresql-for-enterprises-developers-and-agents-on-azure-and-fabric/4573498); [InfoWorld](https://www.infoworld.com/article/4250181/microsoft-adds-horizondb-to-fabric-to-ease-development-of-agent-driven-applications.html))

**AKS becomes a runtime for Foundry models and agents.** Status: preview (Ignite). Open-weight models from Foundry can now be deployed to your own AKS clusters (a limited preview). A new Agent Sandbox extension runs agent-written code in VM-isolated sandboxes, using either Kata microVMs on your own nodes or a serverless runtime on Azure Container Instances, and keeps pre-warmed pools ready. Flex nodes add servers outside Azure to the same AKS cluster. Why it matters: it follows the same pattern as last week's AWS Nitro Sandboxes. Hyperscalers now treat untrusted, model-generated code as a workload class that needs hardware isolation, not just container namespaces. ([Microsoft Tech Community](https://techcommunity.microsoft.com/blog/appsonazureblog/run-models-and-agents-on-your-own-kubernetes-clusters-aks-at-microsoft-ignite-20/4573912); [Microsoft Book of News](https://news.microsoft.com/events/ignite/2026/book-of-news/))

**Azure Catalyst, an agentic migration and modernization service.** Status: GA (Ignite). It combines AI-driven discovery, planning, migration and modernization across Azure and GitHub. It can assess container workloads for AKS or Azure Red Hat OpenShift and plan SQL migrations in waves through Azure Database Migration Service. Why it matters: migration assessment, usually the slowest and most consultant-heavy part of a move, is being automated. Check its wave plans against your own dependency maps before you trust them. ([Azure](https://azure.microsoft.com/en-us/blog/introducing-azure-catalyst-agentic-modernization-and-new-ai-infrastructure-innovations/); [Azure — Ignite roundup](https://azure.microsoft.com/en-us/blog/microsoft-ignite-2026-whats-new-in-azure-the-platform-purpose-built-for-ai/))

### Google Cloud

**Partner Cross-Cloud Interconnect for Microsoft Azure.** Status: preview (announced November 18) in us-east4, us-west2 and europe-west3, with more regions planned as it heads to GA. It provides private connections between Google Cloud and Azure that you set up through the API in minutes, with flat bandwidth-based pricing. Rates and capacity tiers were not published in the post. Google and Microsoft support it jointly. Why it matters: together with the AWS–Azure GA above, every pairing of the big three clouds now has, or is close to having, a managed private link. That makes architectures that split work across clouds (data in one, GPUs or SaaS in another) more practical to operate. ([Google Cloud](https://cloud.google.com/blog/products/networking/cross-cloud-interconnect-for-microsoft-azure))

**GKE supports single-stack IPv6 clusters.** Status: preview on GKE 1.37.1-gke.3020000 (announced November 19). Nodes and pods run with no private IPv4 at all, and each node gets a /112 pod range. IPv4-only destinations are reached through DNS64 and NAT64 on Cloud NAT. At launch it supports TPU v6e and common CPU families (E2, N-series, C3/C4, C4A Axion, Z3), with other accelerators "coming soon". Why it matters: large AI clusters are running out of RFC 1918 address space. IPv6-only pods remove that limit and the NAT layers inside the cluster, but plan for NAT64 egress to legacy IPv4 services. ([Google Cloud](https://cloud.google.com/blog/products/networking/run-aiml-workloads-on-ipv6-only-gke-clusters))

**Sovereign AI in Europe: Gemini moves closer to customer-controlled environments.** Status: mixed (announced November 17). Managed model serving on S3NS's PREMI3NS in France is GA, and PREMI3NS has gained SecNumCloud 3.2 qualification. Confidential External Key Management, in which root keys held outside Google are used only inside attested confidential-computing environments, is in preview. A Data Boundary framework for Switzerland is available now, and one for DORA is planned. Gemini models are coming to the partner-operated Google Cloud Dedicated, and select Gemini models now process data in-region in the EU. Why it matters: regulated EU buyers can now get frontier models and external key control from the same provider, which was the main gap in sovereign-cloud offerings. ([Google Cloud](https://cloud.google.com/blog/products/identity-security/sovereign-ai-on-your-terms-made-with-europe))

**Database Center can test Cloud SQL recommendations on a clone first.** Status: preview, Cloud SQL for PostgreSQL (announced November 19). An "Assess impact" button clones the instance, runs a synthetic benchmark, applies the recommendation to the clone, reruns the benchmark, and reports the change in throughput, latency, CPU and memory before deleting the clone. At launch it covers machine upgrades, Enterprise to Enterprise Plus upgrades, and enabling the data cache. Why it matters: you can justify a costly edition or size upgrade with measured results instead of guesses, without touching production. ([Google Cloud](https://cloud.google.com/blog/products/databases/database-center-assessments-for-cloud-sql-for-postgresql))

## Industry news

**Nvidia posts $115.8B quarter as Rubin ramps.** On November 17, Nvidia reported fiscal Q3 2027 revenue of $115.8 billion, up 103% year on year. Data center revenue was $107.6 billion, and Nvidia guided about $130 billion for the current quarter, assuming no data center compute sales to China. CNBC noted that four customers made up 47% of sales and that Nvidia's own data center lease and cloud-service commitments rose to $102 billion. This was the first report since Jensen Huang's departure. For cloud buyers, it means hyperscaler and GPU-cloud capacity keeps growing quickly, and it is concentrated in a small group of very large customers. ([Nvidia](https://nvidianews.nvidia.com/news/nvidia-announces-financial-results-for-third-quarter-fiscal-2027); [CNBC](https://www.cnbc.com/2026/11/17/nvidia-nvda-earnings-report-q3-2027.html))

**OpenAI signs a 457 MW, six-year AMD capacity deal with TensorWave.** Announced November 16, the dedicated single-tenant capacity uses AMD Instinct MI455X GPUs in Helios rack-scale systems across several US sites. It is due to start operating in the first half of 2027 and be fully deployed by early 2028. It is TensorWave's largest contract, and it comes days after the GPU cloud's planned lease at Fermi's Texas campus fell through. It is more evidence that neoclouds and non-Nvidia silicon are becoming a real second source of frontier-scale capacity. ([Data Center Dynamics](https://www.datacenterdynamics.com/en/news/openai-signs-on-for-457mw-ai-capacity-with-tensorwave/); [TensorWave](https://tensorwave.com/blog/tensorwave-to-provide-openai-with-457-megawatts-of-amd-powered-ai-infrastructure))

**Microsoft traces last week's Microsoft 365 outage to a defect it shipped in July.** Microsoft's preliminary post-incident report blames a July change to its network gateway servers. The change passed load testing and ran without problems until a Teams failover increased traffic while capacity was reduced. The defect then spread across the gateway fleet in under two hours, and at the worst point more than 80% of gateway servers were unresponsive. Microsoft says the final report is due November 20. For architects, the lesson is that a latent bug plus your own failover traffic can take down a fleet that every canary showed as healthy. ([The Register](https://www.theregister.com/2026/11/16/microsoft-blames-monster-email-outage-on-software-defect-introduced-in-july-fix/5310026); [Network World](https://www.networkworld.com/article/4249392/microsoft-outage-a-cascading-failure-that-started-with-an-undetected-bug-2.html))

## Architecture & design patterns

### Sashiko: lessons from an agentic code reviewer for the Linux kernel

*Google Cloud Blog, November 19.* Google's team describes an open-source review pipeline. It gathers full context (callers, struct definitions, subsystem guides), then runs up to seven single-focus specialist reviewers in parallel, covering areas such as locking, resource lifetimes and security. Contested findings go to dedicated verification agents, and the reviewers' own "this is fine" dismissals get the same checking as the bugs they report. The team measured every change against a benchmark of nearly 1,000 real kernel bugs that had passed human review. Commits that got a clean review needed a later fix 0.9% of the time, against 7.6% for commits merged despite critical warnings. Apply it when you build any LLM-based verification step (code review, change approval, policy checks): split finding from verifying, give each agent one narrow job, and test against your own history of past failures. ([Google Cloud](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system))

### Envoy as an AI-aware data plane for models, tokens and MCP

*Google Cloud Blog, November 19.* This post sets out an architecture in which Envoy reads request bodies, not just headers. That lets it route between hosted and self-hosted models with a config change and enforce per-tenant token-per-minute and token-per-day budgets (returning 429 when they run out). With the Gateway API Inference Extension, it can send prompts that share a prefix to the GPU that already holds the matching KV cache. It also routes MCP calls by method and tool name, and calls external guardrail services inline. Google presents this as a direction built on open-source projects, not a GA product. Apply it when several teams share model capacity and you need cost limits, fallbacks and security checks in one place instead of in each agent. ([Google Cloud](https://cloud.google.com/blog/products/networking/the-envoy-agentic-stack-routing-models-tokens-and-mcp))

### Evolving Infra: agent-adaptive LLM serving at scale

*arXiv preprint 2611.12304 (cs.DC), not peer reviewed; submitted November 9, just before this window.* Authors including Ion Stoica and Song Han argue that prefill–decode disaggregated serving breaks down under agentic traffic. Fixed prefill and decode node roles become unbalanced, and KV caches that agents will reuse get evicted between turns. They propose separating compute allocation from KV-cache management, so that nodes can switch roles while reusable caches stay in place. Apply it when you size self-hosted inference for multi-turn agent workloads: treat KV-cache retention as a capacity variable of its own, not just a side effect of GPU count. ([arXiv](https://arxiv.org/abs/2611.12304))

## Takeaway

Ignite week showed hyperscalers treating each other as part of the network. AWS made its private interconnect to Azure generally available, and Google previewed its own Azure link the next day. Almost every pairing of the big three can now be joined with managed, API-provisioned private links instead of hand-built cross-connects. Meanwhile, Azure (Agent Sandbox on AKS), AWS (GPU Lambda, cross-Region inference routing) and Google (Envoy's token-aware data plane) all shipped features that assume AI agents and inference will be spread across regions, clusters and clouds. For architects, multi-cloud designs no longer depend on whether the network can be built. They depend on cost, data residency, and how you isolate and govern the agents running across it.
