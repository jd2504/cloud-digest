## Provider announcements

### AWS

**AWS Lambda raises the on-demand Event Function timeout to 30 minutes.** Status: GA (November 19), in all commercial regions. The limit, previously 15 minutes, now covers synchronous, asynchronous and event source mapping invocations, and can be set to up to 1,800 seconds. On Lambda Managed Instances, synchronous calls get the new 30-minute cap and async/ESM calls keep their 90-minute limit. There are caveats. Synchronous callers such as API gateways may give up before the function finishes. SQS visibility timeouts should be at least six times the function timeout. On-demand Kafka mappings created before this change stay capped at 14 minutes unless you switch them to provisioned mode. Why it matters: batch steps and longer agent or ETL tasks that used to need Step Functions or Fargate can now stay in a single function. Check the timeouts on everything upstream before you raise it. ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-30-minute-ondemand-event-functions/); [AWS Compute Blog](https://aws.amazon.com/blogs/compute/announcing-30-minute-timeout-for-on-demand-aws-lambda-event-functions/))

**Amazon S3 doubles the read request rate for general purpose buckets.** Status: GA (November 20), in all regions, applied automatically at no extra charge beyond standard request pricing. Each partitioned prefix now supports at least 11,000 GET/HEAD requests per second, up from 5,500. Write rates are unchanged at 3,500 per second. Why it matters: read-heavy workloads such as AI training data loaders, data lakes and media origins need less key sharding to avoid 503 Slow Down errors. Some AWS docs still cite the old figure, so update capacity-planning assumptions from the S3 performance guide. ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-s3-increases-read-request-rate/); [AWS docs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html))

**Amazon CloudWatch Omni ingests Microsoft Azure logs, metrics and traces.** Status: available (November 21). Omni can now collect Azure resource logs, Azure Monitor platform metrics, VNet flow logs and Application Insights traces through connectors linked to a Microsoft Entra ID tenant, from all Azure public regions. Pricing follows Omni's standard ingest, storage and query rates. The announcement gives no Azure-specific rate. Why it matters: it builds on last week's AWS–Azure Interconnect GA. Teams running both clouds can use one observability backend instead of two consoles or a third-party tool. Estimate ingest volume first, because flow logs add up quickly. ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-cloudwatch-omni-microsoft-azure/); [AWS pricing](https://aws.amazon.com/cloudwatch/omni/pricing/))

**Amazon EventBridge can deliver to Amazon MSK, and Scheduler gains 589 API actions.** Status: available (November 20). Custom event buses on the enhanced bus can now target MSK (managed Kafka) topics directly, in all regions with the enhanced bus. Separately, EventBridge Scheduler added 589 API actions across 81 services as direct targets, in all commercial regions where Scheduler runs. Why it matters: bridging events into Kafka no longer needs a Lambda or Pipes step in between. More scheduled operational tasks can call AWS APIs directly, without glue functions. ([AWS — MSK target](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-eventbridge-msk-target/); [AWS — Scheduler](https://aws.amazon.com/about-aws/whats-new/2026/11/eventbridge-scheduler-new-api-actions/))

**Amazon Bedrock AgentCore runtime instances support EC2 G7 GPUs.** Status: available (November 20) in N. Virginia, Ohio, Oregon, Frankfurt, London, Stockholm, Mumbai and Sydney. Why it matters: agents that run local models or GPU tools can now run on AgentCore's managed runtime, so you don't have to split the agent loop from its inference host. ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/11/agentcore-ec2-g7/))

### Microsoft Azure

Azure published little in the window after Ignite's launches, which we covered on Thursday. One action item:

**Azure Pipelines retires a set of deprecated, little-used tasks starting November 24.** Status: retiring. From tomorrow, pipelines that still reference these tasks show retirement warnings. When the tasks are removed on March 15, 2027, those pipelines fail with a blocking error. Why it matters: release pipelines that rarely run, such as DR runbooks and yearly jobs, are the ones most likely to break unnoticed. Search your YAML and classic pipelines for the listed tasks now. ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/devops/pipelines/tasks/task-retirement?view=azure-devops))

### Google Cloud

**Ambient networking for GKE, a managed sidecarless service mesh.** Status: GA (November 21). A per-node L4 Envoy proxy provides automatic mTLS with managed workload identities, authorization policies, load balancing, and L4/L7 telemetry, without injecting a sidecar into every pod. It can be enabled on new or existing clusters, and Google upgrades it during normal GKE maintenance without restarting application pods. Network Services Monitoring, also newly available, shows the metrics. Google claims up to 10x lower resource use for L4 mesh features. Pricing is on the GKE service networking pricing page. Why it matters: the cost and restart churn of sidecars are the main reasons teams skip a mesh. A managed ambient mode makes mTLS-everywhere zero trust the cheap default inside a cluster. ([Google Cloud](https://cloud.google.com/blog/products/networking/ambient-networking-for-gke-sidecarless-service-mesh))

**Unified Access Policies in Cloud IAM.** Status: preview, at no additional cost (November 21). Allow and deny rules now share one policy schema. A single policy can bind to up to 25 organizations, folders or projects, and permissions support wildcards and exclusions. Central security teams can set org-level guardrails and let folder and project admins bind policies themselves. AI agents are first-class principals that can be scoped individually or by pool. The feature is supported in the console, gcloud, Terraform and the IAM v3 API, and is evaluated alongside existing allow and deny policies. Why it matters: it addresses a real governance gap. Agents get their own identities and least-privilege policies instead of shared service accounts, and guardrails can be written once instead of copied into every project. ([Google Cloud](https://cloud.google.com/blog/products/identity-security/how-to-simplify-cloud-access-with-unified-access-policies))

**Cloud Storage object enrichments.** Status: preview (November 20), in the console and API. The service runs five first-party models over images and PDFs in a bucket: object detection, face detection, labeling, explicit-content detection and PDF classification. It writes the results as key-value "object context" stored with each object, which follows the object through copy, move and replication. Google puts the cost of enriching 10 million images or PDFs at about $700. Gemini-based summarization, extraction and transcription are available on request. Why it matters: metadata extraction moves into the storage layer, so you no longer need a separate event-driven pipeline to label data before agents or BigQuery can use it. ([Google Cloud](https://cloud.google.com/blog/products/storage-data-transfer/cost-effective-ai-context-extraction-from-unstructured-gcs-data))

**In-place migration to GKE Dataplane V2.** Status: preview (November 20), for VPC-native clusters on GKE 1.35+. Routes-based clusters and clusters running Calico are not supported. A single gcloud command starts a rolling move from iptables/kube-proxy to the eBPF/Cilium dataplane. The rollout respects maintenance windows and can be rolled back until you finalize it. Why it matters: older clusters can get Dataplane V2's network policy enforcement and observability without building a parallel cluster and moving workloads. Run the IP-capacity and compatibility preflight checks first. ([Google Cloud](https://cloud.google.com/blog/products/networking/gke-dataplane-v2-in-place-migration))

## Industry news

**CrowdStrike agrees to buy Zscaler in a $43.9 billion all-stock deal.** The merger agreement was signed November 22 and announced November 23, alongside CrowdStrike's Q3 results. Zscaler's founder, Jay Chaudhry, will keep running the Zscaler business and join CrowdStrike's board. Zscaler cancelled its earnings call and withdrew its guidance. The combined company will sell endpoint and cloud workload protection together with Zscaler's zero-trust network access and secure web gateway. For architects, two major parts of the zero-trust stack will now come from one vendor, so expect bundling and tighter integration, and review roadmap and contract risk if you rely on either product. ([CrowdStrike](https://ir.crowdstrike.com/news-releases/news-release-details/crowdstrike-acquire-zscaler-bringing-network-security-and-zero); [Zscaler](https://www.zscaler.com/press/crowdstrike-acquire-zscaler-bringing-network-security-and-zero-trust-falcon-platform); [CNBC](https://www.cnbc.com/2026/11/23/crowdstrike-to-buy-zscaler.html))

**Microsoft's final report on the Microsoft 365 outage blames tests run on the wrong hardware.** The final post-incident report, released November 20, says the July gateway defect affected only newer, higher-core-count servers. Microsoft's load tests ran on older machines, so they missed it. Automated recovery wasn't built for a fleet that was almost entirely unresponsive, and normal rollback couldn't quickly undo a months-old change. Unlike Teams, Exchange had no alternative infrastructure to fail over to. Microsoft lists 13 fixes, including workload-isolated gateway pools, load testing on its newest hardware and limits on traffic redistribution, with some due by March 2027. Lesson: test on the hardware you actually run in production, and make sure your safeguards can't turn a partial failure into a fleet-wide one. ([GeekWire](https://www.geekwire.com/2026/microsofts-final-outlook-outage-report-details-testing-gaps-and-safeguards-that-backfired/); [BleepingComputer](https://www.bleepingcomputer.com/news/microsoft/microsoft-says-months-old-bug-caused-global-microsoft-365-outage/))

**Rackspace Spot breach exposed customers' Kubernetes Secrets.** Rackspace told customers that an attacker used leaked credentials to get into its managed Kubernetes platform on November 17. The attacker could act as users in some customer organizations, create pods, read Secrets, and list nodes and volumes. Rackspace revoked tokens, rotated keys and published indicators of compromise. The Spot console stayed down for days, and Rackspace said service was fully restored on November 21. Customers are told to treat every Secret in affected clusters as compromised. The incident shows why Kubernetes Secrets shouldn't hold long-lived credentials: use workload identity or an external secrets manager with short-lived credentials, so one leaked credential doesn't expose every downstream system. BleepingComputer first reported the customer notice. ([BleepingComputer](https://www.bleepingcomputer.com/news/security/rackspace-spot-breach-let-hackers-access-customer-kubernetes-secrets/); [SC Media](https://www.scworld.com/brief/rackspace-discloses-security-breach-of-spot-cloud-platform))

## Architecture & design patterns

### How Bee implemented Zero Operator Access for personal AI on AWS

*AWS Architecture Blog, November 20.* Bee, a personal AI wearable, describes a design in which its own engineers, Amazon staff and AWS operators can't read user data. The user's device releases decryption keys only to EC2 instances whose software it has verified through instance attestation, and Nitro protects the infrastructure layer. Images have no SSH, SSM or shell access, instances are replaced rather than rebooted, and they run in isolated subnets with no internet egress. Inference servers never receive keys, and keys expire after seven days without user activity. **When to use it:** when you process sensitive personal or regulated data with AI and need to prove to customers that operators can't access it, not just promise it. ([AWS](https://aws.amazon.com/blogs/architecture/how-bee-implemented-zero-operator-access-for-personal-ai-on-aws/))

### A "wind tunnel" for testing data agents

*Google Cloud Blog, November 21.* Google describes an internal simulator that builds a complete synthetic data estate (schemas, rows, event history, documents and chat threads) from a short plain-English description. An LLM is used once to compile a frozen blueprint of systems, people, metrics and beliefs, including deliberately wrong beliefs that act as traps. Tables and SQL answer keys are then generated deterministically from the blueprint and a seed, and the model is used again only to write documents. Agents get read-only tools against this estate, so their answers can be scored exactly and reproducibly. No product was announced. **When to use it:** when you need repeatable regression tests for agents that query enterprise data, without exposing production data or depending on a non-deterministic evaluator. ([Google Cloud](https://cloud.google.com/blog/products/data-analytics/a-data-simulator-to-test-agents))

### Replacing API keys with identity for model access

*Google Cloud Blog, November 21.* The guide treats long-lived AI API keys as bearer tokens that aren't tied to any person or workload, and lays out a migration path. Developers sign in with short-lived application-default credentials. Production workloads run under dedicated service accounts with a single narrow role, and access is granted through groups. Any remaining third-party secrets go into Secret Manager, and the old keys are deleted. Spend caps, guardrails and monitoring limit the damage if something leaks. **When to use it:** as a standard pattern for any team calling hosted models. Combined with the Rackspace breach above, the theme of the week is to replace static credentials with workload identity. ([Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/how-to-fix-your-teams-api-keys))

## Takeaway

With re:Invent a week away, the providers shipped changes that remove long-standing design limits rather than headline products. Lambda's 30-minute timeout and S3's doubled read rate mean fewer workarounds: less orchestration glue and less key sharding. The other theme was identity as the security boundary. Google made a sidecarless mTLS mesh GA and previewed IAM policies that treat agents as first-class principals. AWS published a zero-operator-access reference design. The Rackspace Spot breach showed the cost of static credentials stored in cluster Secrets. CrowdStrike's planned purchase of Zscaler points the same way, toward zero-trust stacks sold by fewer vendors. For architects, it is a good week to revisit timeout and throughput assumptions and to retire long-lived keys.
